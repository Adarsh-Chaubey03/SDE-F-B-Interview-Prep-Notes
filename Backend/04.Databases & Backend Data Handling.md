# Databases & Backend Data Handling

## 1. SQL vs NoSQL

### SQL

Relational databases store data in tables with predefined schemas.

Examples:

* MySQL
* PostgreSQL
* SQL Server
* Oracle

Example:

```text
Users
--------------------------------
id | name   | email
1  | Adarsh | a@x.com
2  | Rahul  | r@x.com
```

SQL databases are strong when you need:

* Structured relationships
* Complex queries
* Transactions
* Strong consistency
* Referential integrity

### NoSQL

NoSQL databases use models such as documents, key-value pairs, graphs, or wide columns.

MongoDB is a **document database**.

Example:

```json
{
  "_id": 123,
  "name": "Adarsh",
  "email": "a@x.com"
}
```

NoSQL databases can be useful when:

* Data structure changes frequently
* Horizontal scaling is important
* Document-oriented data fits the application
* Flexible schemas are useful

Do not say:

> SQL is better than NoSQL.

The choice depends on the application's requirements.

---

# 2. MongoDB

MongoDB is a document-oriented NoSQL database.

Its main concepts are:

```text
Database
   ↓
Collection
   ↓
Documents
```

A document is stored in BSON, a binary representation similar to JSON.

Example:

```json
{
  "_id": "123",
  "name": "Adarsh",
  "skills": ["React", "Node.js"],
  "experience": 1
}
```

Unlike a traditional relational table, MongoDB documents can contain nested objects and arrays.

---

# 3. MongoDB Schema Design

A major design decision is whether related data should be:

### Embedded

```json
{
  "name": "Adarsh",
  "address": {
    "city": "Imphal",
    "country": "India"
  }
}
```

Useful when related data is usually accessed together.

### Referenced

```json
{
  "userId": 123,
  "addressId": 456
}
```

Useful when the related data is large, shared, or independently managed.

The decision depends on:

* Access patterns
* Data size
* Update frequency
* Relationship structure

# 4. Database Indexes

An index is a data structure that helps the database find records more efficiently.

Without a suitable index, the database may need to scan many or all records.

Example:

```text
Users
 ↓
Search by email
 ↓
Index on email
 ↓
Faster lookup
```

MongoDB example:

```javascript
db.users.createIndex({ email: 1 });
```

An index can significantly improve read performance.

### Tradeoff

Indexes are not free.

They:

* Consume storage
* Increase write/update overhead
* Require maintenance

Therefore, don't create indexes blindly.

---

# 5. Query Optimization

If an API is slow because of a database query, investigate:

1. Query structure
2. Indexes
3. Amount of data being returned
4. Filtering conditions
5. Sorting
6. Joins/lookups where applicable
7. Execution plan

The goal is not simply:

> "Add an index."

The correct approach is:

> Identify the expensive operation, inspect the query plan, and then optimize based on actual access patterns.

# 6. MongoDB Aggregation

MongoDB's aggregation framework processes documents through stages.

Example:

```javascript
db.orders.aggregate([
  { $match: { status: "completed" } },
  { $group: {
      _id: "$userId",
      total: { $sum: "$amount" }
  }}
]);
```

Conceptually:

```text
Documents
   ↓
$match
   ↓
$group
   ↓
Result
```

Common stages include:

```text
$match
$group
$sort
$project
$limit
$lookup
```

Aggregation is useful for filtering, transforming, grouping, and calculating data.

---

# 7. Transactions

A transaction groups multiple database operations into a single logical unit.

The key property is:

> Either all required operations succeed, or the transaction is rolled back.

Example:

```text
Transfer ₹100
   ↓
Deduct ₹100 from Account A
   ↓
Add ₹100 to Account B
```

If the deduction succeeds but the addition fails, the system should not leave the database in an inconsistent state.

Transactions are particularly important for operations where multiple changes must remain consistent.

---

# 8. ACID

Traditional relational transactions are commonly described using ACID:

### Atomicity

All operations in a transaction succeed or the transaction is rolled back.

### Consistency

The database moves from one valid state to another valid state.

### Isolation

Concurrent transactions should not incorrectly interfere with one another.

### Durability

Once committed, the data should survive failures according to the database's durability guarantees.

For interviews, understand the concepts rather than memorizing the expansion alone.

# 9. Connection Pooling

Opening a new database connection for every request can be expensive.

Instead, applications commonly use a **connection pool**.

```text
Application
     ↓
Connection Pool
 ┌───┼───┬───┐
 C1  C2  C3  C4
     ↓
 Database
```

When a request needs a database connection:

```text
Request
   ↓
Get available connection
   ↓
Execute query
   ↓
Release connection
```

Benefits:

* Reduces connection establishment overhead
* Reuses existing connections
* Handles concurrent database operations more efficiently

An excessively large pool can also be harmful because the database has limited resources.

# 10. N+1 Query Problem

The N+1 problem occurs when an application performs:

```text
1 query → fetch N records
N queries → fetch related data for each record
```

Example:

```text
Get 100 users
   ↓
1 query

Then for every user:
   ↓
Get orders
   ↓
100 queries
```

Total:

```text
1 + 100 = 101 queries
```

This can cause serious performance problems.

Possible solutions include:

* Joins
* Batch queries
* Aggregation
* Eager loading
* Data loaders/caching where appropriate

The correct solution depends on the database and access pattern.

---

# 11. Pagination

Returning thousands of records in one API response is inefficient.

Instead, APIs commonly support pagination.

Example:

```text
GET /users?page=2&limit=20
```

Possible response:

```json
{
  "data": [...],
  "page": 2,
  "limit": 20,
  "total": 500
}
```

Two common approaches are:

### Offset pagination

```text
OFFSET 20
LIMIT 20
```

Simple, but can become inefficient for very large datasets or frequently changing data.

### Cursor pagination

Uses a stable cursor to continue from a previous position.

It is generally better suited to large or continuously changing datasets.

# 12. Database Security

Never directly trust data received from the frontend.

The backend should perform:

* Input validation
* Authorization checks
* Proper query construction
* Schema validation
* Authentication where required

Never store passwords as plaintext.

Passwords should be stored using a strong password-hashing algorithm such as:

```text
bcrypt
scrypt
Argon2
```

Hashing is different from encryption:

```text
Hashing    → One-way transformation
Encryption → Reversible with a key
```

# 13. Backend Request → Database Flow

A typical Node.js application can follow:

```text
HTTP Request
     ↓
Middleware
     ↓
Controller
     ↓
Service
     ↓
Repository / Database Layer
     ↓
Database
     ↓
Result
     ↓
Service
     ↓
Controller
     ↓
HTTP Response
```

This separation keeps HTTP handling, business logic, and data access from becoming tightly coupled.
